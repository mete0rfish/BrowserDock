# 부록 B. 설계 선택 해설

이 페이지는 기준 명세와 구현에서 확인되는 선택을 학습용으로 해설합니다. 과거 회의에서 특정 대안을 검토했다는 기록을 새로 만들어 내는 공식 ADR은 아닙니다. 아래의 비용과 재검토 조건은 현재 구조를 이해하기 위한 분석입니다.

## 브라우저 수명과 attachment 수명 분리

**확인되는 선택:** Chrome을 별도로 소유하고, WebDriver 연결을 해제해도 Chrome과 독립 CDP를 유지합니다.

**얻는 점:** 자동화 연결 교체를 브라우저 재시작과 분리할 수 있습니다. CDP 제어도 Selenium 객체의 수명에 직접 묶이지 않습니다.

**부담:** 프로세스·소켓·세션의 부분 실패를 조정해야 하며, 어느 자원을 정리했는지 구분해야 합니다. “driver.Dispose 하나로 끝내기”보다 lifecycle 구현이 복잡해집니다.

외부 Chrome 소유권 인수나 keep-alive 전환을 추가한다면 종료 책임을 먼저 다시 정의해야 합니다.

## raw Selenium 객체 대신 guarded API

**확인되는 선택:** 사용자에게 `IWebDriver`와 `IWebElement`를 직접 반환하지 않습니다. lease와 `ElementRef`를 통해 상태 및 epoch를 확인합니다.

**얻는 점:** 이전 attachment의 참조를 라이브러리 경계에서 거부하고, 원치 않는 직접 Quit 경로를 줄일 수 있습니다.

**부담:** Selenium 전체 API를 그대로 제공하지 않으므로 명령을 추가할 때 공개 계약과 오류 매핑을 설계해야 합니다. 편리하다는 이유만으로 raw 객체를 공개하면 이 안전 경계를 우회하게 됩니다.

## 명시적인 target 선택

**확인되는 선택:** 여러 탭이 모호하면 최근 탭이나 배열 순서를 기준으로 추측하지 않습니다. CDP와 WebDriver 대상은 임시 marker로 대응시킵니다.

**얻는 점:** 잘못된 페이지에서 명령을 실행할 위험을 줄입니다.

**부담:** 호출자가 대상 선택을 명확히 해야 하고, 탭 종료·생성 경합과 marker 정리까지 다뤄야 합니다. 자동 선택 정책을 추가한다면 모호성 처리와 관찰 가능한 계약부터 정해야 합니다.

## epoch와 generation 분리

**확인되는 선택:** 명령 진입을 닫을 때 epoch를 바꾸고, 성공적인 attachment 생성 뒤 generation을 증가시킵니다.

**얻는 점:** 재연결 성공 전에도 이전 참조를 차단할 수 있습니다.

**부담:** 두 숫자가 서로 다른 의미라는 설명과 테스트가 필요합니다. 단일 재연결 횟수로 합치려면 실패 중 참조 무효화 조건을 먼저 증명해야 합니다.

## 원본을 보존하는 opt-in 패치

**확인되는 선택:** 기본은 비활성화이며, 패치할 때도 원본을 수정하지 않고 검증된 캐시 사본을 사용합니다. 검증 실패를 조용한 원본 fallback으로 숨기지 않습니다.

**얻는 점:** 원본 무결성과 실제 실행한 산출물의 추적 가능성을 유지할 수 있습니다.

**부담:** 버전별 recipe와 정확한 패턴 개수, hash와 캐시 경쟁을 검증해야 합니다. 합성 테스트 통과만으로 실제 바이너리 호환성을 선언할 수 없습니다.

## 앞으로 결정 기록을 추가하는 양식

새 결정은 문제, 확인한 제약, 실제 검토한 대안, 선택, 장단점, 검증 계획, 재검토 조건을 기록합니다. 아직 제안인 내용에는 '제안'을 표시하고 구현 완료 상태와 섞지 않습니다.

```text
제목:
상태: 제안 / 수용 / 대체됨
문제와 근거:
실제로 검토한 대안:
선택과 이유:
예상되는 비용:
검증 방법:
다시 검토할 조건:
관련 이슈·PR·커밋:
```
