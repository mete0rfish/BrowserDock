# SeleniumBase behavioral compatibility matrix

This is the contract baseline for [issue #25](https://github.com/mete0rfish/BrowserDock/issues/25) under [Epic #24](https://github.com/mete0rfish/BrowserDock/issues/24). It defines selected observable behaviors to implement, not a claim that BrowserDock already ports SeleniumBase. BrowserDock is an independent project, not an official SeleniumBase .NET binding.

Reviewed on 2026-09-28 against BrowserDock [`687d77e270cc49da02dacd312af5fc355aad9289`](https://github.com/mete0rfish/BrowserDock/tree/687d77e270cc49da02dacd312af5fc355aad9289) and SeleniumBase **4.53.7**, commit [`4ee7dfc4ae83c19385f5ac129f2cda0cfa863d80`](https://github.com/seleniumbase/SeleniumBase/tree/4ee7dfc4ae83c19385f5ac129f2cda0cfa863d80). The reference runner pins the same version in its [manifest](../tests/seleniumbase-reference/scenarios.json). This review is static; no new browser or upstream-comparison result is established here.

## Shared .NET contract

These rules apply to every matrix entry, including proposed APIs. Existing gaps in #26–#28 remain gaps; this document does not fix them.

- **Ownership:** preserve exact PID/create-time identity, owned process trees, loopback endpoint verification, exclusive profiles and marker-checked temporary-profile deletion. A facade composes the existing engine; it cannot launch an untracked process, expose raw Selenium objects, or use private reflection. Requested but unsupported settings fail explicitly.
- **Configuration:** ordinary startup remains unchanged unless UC is explicitly enabled. #30 defines a versioned opt-in profile with published effective arguments, scripts and recipe requirements. Caller settings and per-call policies are captured once (#26); incompatible profile/patch/script/navigation requests fail before resource creation or navigation. Enabling UC cannot silently discard explicit settings or fall back when a required recipe is unavailable (#31). The profile must record script order and deduplicate its own registrations; arbitrary caller scripts and strategy objects are not claimed to be deeply frozen.
- **Targets and context:** select a stable `TargetKey`; reject ambiguity rather than guessing from window order. Replacement closes only the controlled page and identifies the new page explicitly. Frame-sensitive compatibility operations carry a target and frame locator path. Current Core `FindAsync` restores that path from the top document (empty path means top document); it does not inherit a prior `SwitchToFrameAsync` selection. #32 must make this difference explicit in its facade and tests.
- **References:** rotate `AttachmentEpoch` before disconnect; increment `SessionGeneration` only on successful attachment. Old leases/elements cannot revive. Locator reacquisition is explicit or opt-in and uses the same target/frame path. Document replacement invalidates old DOM references even without an epoch change. Scalar/JSON results are snapshots. Future CDP elements use target + document/execution-context + transport identity (#35), not a WebDriver epoch; navigation, target closure and transport recovery invalidate them.
- **Completion:** navigation explicitly selects `Commit`, `DOMContentLoaded`, `Load` (Core default), or `NetworkIdle`. These are transport/page milestones, not proof of expected application content. Same-document navigation and downloads remain distinct results. Actions complete at their documented command/condition boundary; a click or key submission is not an implicit page-load wait.
- **Budgets and cancellation:** admission, waits, action and requested delay consume one operation budget. An expired queue wait must make zero remote calls and leave a healthy attachment intact. Preserve caller cancellation separately from `OperationTimedOut`; do not retry non-idempotent actions after an uncertain outcome. Once detachment or failed-command cleanup starts, finish owned-resource cleanup within its separate bounded scope (currently at most ten seconds), report health/cleanup failures, and never remove a newer attachment. #27 implements the admission/error-mapping and lifecycle-gate fix; portable and Windows acceptance evidence must be recorded separately. Navigation errors retain whether the browser may have advanced; cancellation cannot undo a submitted navigation or native input.
- **Final disposal:** `Browser.StopAsync`/`DisposeAsync` mean final cleanup, including owned Chrome. Disposing a `WebDriverLease` only releases that lease. Neither is a reconnect boundary. A future facade also uses explicit methods for reconnection; Python `with driver:` semantics are not mapped to .NET `using`.

### Disconnected duration is not an operation timeout

SeleniumBase `reconnect(timeout=...)` sleeps between service stop and start. `uc_open_with_reconnect(reconnect_time=...)` passes that delay; `uc_open_with_disconnect(timeout=...)` sleeps before returning while still disconnected. Those parameters are durations, not .NET deadline budgets. Python string sentinels such as `"disconnect"` and `"breakpoint"` are not .NET duration values.

The #29 `Browser.Uc` facade uses a typed **minimum disconnected duration**, measured with a monotonic clock from confirmed driver exit. If the operation starts in CdpOnly, start the clock when that operation confirms Chrome/CDP health and driver absence; do not credit an unknown earlier disconnected interval. Navigation can progress during that duration. Reattach (or return from the disconnect helper) only after both the requested navigation milestone and that minimum duration. Zero means no additional hold; omitted means an explicitly documented zero default, a deliberate deviation from upstream helper defaults. Negative, non-finite, or values exceeding the operation budget fail before side effects. Runtime budget exhaustion still times out and leaves a healthy browser disconnected. No synchronous sleep or implicit interactive breakpoint is introduced.

Current Core `NavigationOptions.ReconnectDelay` instead starts **after navigation completes**, only for `Detached` with reconnection. It is not an alias for the proposed duration and retains that meaning. `BrowserTimeouts.Navigation` bounds the entire Core operation; `BrowserTimeouts.Reconnect` additionally bounds the subsequent attachment phase. `ReconnectWebDriverAsync` itself requires `CdpOnly` and adds no hold. #28 rejects `Standard` plus `ReconnectAfterNavigation=true`, and any delay (including zero) without Detached reconnection. Null/zero add no intentional hold in the supported combination. Negative delays or delays at least as long as the captured Navigation timeout fail before health probing or lifecycle side effects. Smaller delays still consume the operation budget, so slow navigation can cause a runtime timeout. Portable preflight and separate Windows-browser evidence must remain distinct.

### HTTP preflight and dispatch policy

Do not reproduce SeleniumBase `get`'s separate HTTP request or challenge/status heuristics in either phase. Keep browser traffic, explicit navigation modes, cookies and proxies under one browser contract. There is no heuristic fallback from Standard to Detached and no hidden WebDriver reconnect from a CDP operation. Any future heuristic policy needs separate scope and opt-in acceptance. Require an absolute, enabled `Uri`; upstream URL guessing and permissive argument coercion are intentional deviations. Cloudflare/WAF/CAPTCHA outcomes, automatic solving and universal fingerprint indistinguishability are not acceptance gates.

## Modern, Legacy and platform contract

The behavioral requirements apply to both modern Core and the C# 7.3-friendly, `Task`-based `BrowserDock.Legacy` facade. New supported operations need equivalent options, results, typed errors, cancellation and reference invalidation on both surfaces; a missing facade must be recorded as an explicit unsupported surface, not marked Equivalent. Do not expose records, required/init members, `ValueTask` or `IAsyncDisposable` as requirements for Legacy consumers. Await final cleanup in `try/finally`; do not add synchronous wrappers that block UI threads.

The baseline execution matrix is Core net8.0/net10.0 and Legacy net481/net8.0/net10.0 on Windows 11 x64, an interactive desktop, headed Chrome and a tested Chrome/ChromeDriver pair. Common protocol tests on other hosts establish no browser-hosting support there. General native input additionally requires foreground/focus, screen scaling and session availability checks; RDP lock and UAC boundaries are explicit unsupported conditions unless separately verified. Phase 2 removes the driver requirement for Pure CDP, not browser/platform ownership checks.

[support.md](support.md) governs future releases: .NET 10 is the primary target; reassess .NET 8 after 2026-11-10 with explicit compatibility notice, not automatic TFM removal. Framework 4.8.1 uses the supported Legacy surface. A new phase does not silently broaden platforms, browsers, runtimes or the verified version matrix.
